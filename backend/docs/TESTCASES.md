# TESTCASES — รายการทดสอบทั้ง 52 ข้อ พร้อม status ที่ควรได้

ไฟล์นี้อธิบายว่า request แต่ละอันใน Postman collection **ทดสอบอะไร** และ **ควรได้ status เท่าไหร่**
ใช้คู่กับ [POSTMAN.md](POSTMAN.md) (วิธี import และรัน) และ [API.md](API.md) (รายละเอียด endpoint)

**ผลรวมที่ควรได้: 52 requests ผ่านทั้งหมด / 129 assertions ผ่านทั้งหมด / 0 failed**

---

## ทำความเข้าใจ status code ก่อน

| Code | ชื่อ | แปลว่า | เจอตอนไหน |
|---|---|---|---|
| **200** | OK | สำเร็จ | GET / PUT / PATCH / DELETE ที่ทำงานได้ |
| **201** | Created | สร้างข้อมูลใหม่สำเร็จ | POST ที่สร้างเรคอร์ดใหม่ |
| **400** | Bad Request | พารามิเตอร์ใน URL ผิดรูป | `:id` ไม่ใช่ตัวเลข (จาก `ParseIntPipe`) |
| **403** | Forbidden | มีตัวตนแต่ไม่มีสิทธิ์ | customer พยายามบันทึกการรับสินค้า |
| **404** | Not Found | ไม่มีข้อมูลนั้น / ไม่มี endpoint นั้น | id ที่ไม่มีในฐานข้อมูล |
| **409** | Conflict | คำขอถูกต้อง แต่ชนกับสภาพข้อมูลปัจจุบัน | อีเมลซ้ำ, สต็อกไม่พอ, ลบของที่ถูกอ้างอิงอยู่ |
| **422** | Unprocessable Entity | body ส่งมาไม่ครบหรือผิดกฎ | ขาดฟิลด์บังคับ, ค่าไม่อยู่ในชุดที่กำหนด |
| **500** | Internal Server Error | โค้ดพัง | **ไม่ควรเจอเลย** ถ้าเจอคือมีบั๊ก |

> **ต่างกันตรงไหนระหว่าง 422 กับ 409**
> 422 = "ข้อมูลที่ส่งมาผิดตั้งแต่แรก" (ไม่ส่ง `quantity` มา) — แก้ที่ body
> 409 = "ข้อมูลถูกต้อง แต่ทำไม่ได้ตอนนี้" (สั่ง 100 ชิ้นแต่เหลือ 5) — แก้ที่สภาพข้อมูล

## 07 — Negative Tests (10 requests) — สำคัญที่สุดสำหรับการส่งงาน

**ทุกข้อในโฟลเดอร์นี้ "ผ่าน" เมื่อ API ปฏิเสธคำขอได้ถูกต้อง**
ถ้าข้อไหนได้ 200 หรือ 201 แปลว่า **ระบบมีช่องโหว่** — ไม่ใช่เรื่องดี

| # | Request | Status | ทดสอบว่าระบบกันอะไร |
|---|---|---|---|
| 40 | `GET /api/ไม่มี-endpoint-นี้` | **404** | ยิง path มั่วแล้วต้องไม่พัง ต้องตอบ 404 ในรูปแบบเดียวกับ error อื่น |
| 41 | `GET /api/v1/users/999999` | **404** | id ที่ไม่มีในฐานข้อมูล ต้องไม่ตอบ `null` แต่ต้องเป็น 404 |
| 42 | `POST /api/v1/users` ไม่ส่ง email/phone | **422** | **DTO + class-validator ทำงาน** — กันข้อมูลไม่ครบตั้งแต่ก่อนถึงฐานข้อมูล |
| 43 | `POST /api/v1/users` อีเมลซ้ำ | **409** | **unique constraint ทำงาน** — Prisma โยน `P2002` แล้ว filter แปลงเป็น 409 |
| 44 | `POST /api/v1/products` พรีออเดอร์ไม่ระบุวันปิดรับ | **422** | **กฎทางธุรกิจทำงาน** — เป็นพรีออเดอร์ต้องมี `preorder_end_date` เสมอ |
| 45 | `POST /api/v1/orders` delivery ไม่ระบุที่อยู่ | **422** | กันสั่งจัดส่งโดยไม่มีที่อยู่ส่ง |
| 46 | `POST /api/v1/orders` สั่ง 999999 ชิ้น | **409** | **กันสต็อกติดลบ** — และเพราะอยู่ใน transaction สต็อกที่ตัดไปก่อนหน้าต้องถูก rollback หมด |
| 47 | `POST /api/v1/pickup-logs` โดยใช้ `staff_id` ของ customer | **403** | **กันคนไม่มีสิทธิ์** — ตรวจ `role` ก่อนบันทึกเสมอ |
| 48 | `POST /api/v1/pickup-logs/verify` รหัสมั่ว | **404** | กันคนเดารหัสรับสินค้า |
| 49 | `DELETE /api/v1/users/1` (มีออร์เดอร์อยู่) | **409** | **กันข้อมูลกำพร้า** — ลบผู้ใช้ทิ้งไม่ได้ถ้ามีประวัติการซื้อ |

| # | Request | Status | ทดสอบอะไร |
|---|---|---|---|
| 50 | `DELETE /api/v1/orders/:id` | **200** | ลบออร์เดอร์ทดสอบ + คืนสต็อก |
| 51 | `DELETE /api/v1/products/:id` | **200** | ลบสินค้าทดสอบ (สมุดโน้ต) — variants หายตามแบบ cascade |
| 52 | `DELETE /api/v1/products/:id` | **200** | ลบสินค้าทดสอบ (แจ็คเก็ตพรีออเดอร์) |

> ถ้ายังมีออร์เดอร์อ้างถึงสินค้าอยู่ จะได้ **409** แทน — เป็นการยืนยัน `onDelete: Restrict` ทางอ้อม

## ถ้าผลไม่ตรงกับตารางนี้

| อาการ | ความหมาย |
|---|---|
| ข้อ 1–2 ไม่ผ่าน | เซิร์ฟเวอร์ไม่ได้รัน หรือต่อฐานข้อมูลไม่ได้ — แก้ก่อนแล้วค่อยรันใหม่ |
| ข้อ 4 ได้ 404 | ยังไม่ได้ `npm run seed` |
| ข้อ 5 ได้ 409 | ข้อมูลทดสอบจากรอบก่อนค้างอยู่ — สั่ง `npm run seed` แล้วรันใหม่ |
| ข้อ 24/25 ได้ 201 แต่ assertion เรื่องยอดเงินไม่ผ่าน | **สูตรคำนวณยอดรวมผิด** — ต้องแก้ ไม่ใช่แค่แก้ตัวเลขใน test |
| โฟลเดอร์ 07 ข้อไหนได้ 200/201 | **ระบบมีช่องโหว่** ตรงจุดนั้น |
| โฟลเดอร์ 04–06 ไม่ผ่านเป็นแถว | ยิงข้ามลำดับ ตัวแปร `new_*` ยังว่าง — ใช้ Run collection แทนการยิงทีละอัน |
| เจอ 500 | มีบั๊กในโค้ด — ดู error ที่หน้าต่างที่รัน `npm run dev` |
