## 2026-09-24 — รอบที่ 13: แก้บั๊ก "ข้อมูลซ้ำ: order_number ถูกใช้ไปแล้ว"

### อาการ

กดยืนยันคำสั่งซื้อแล้วขึ้นข้อความสีแดงว่า **"ข้อมูลซ้ำ: order_number ถูกใช้ไปแล้ว"** (HTTP 409) สั่งซื้อไม่ผ่าน

### สาเหตุ

โค้ดเดิมออกเลขที่ออร์เดอร์จาก **จำนวนออร์เดอร์ที่มีอยู่**

```ts
const sequence = (await tx.order.count()) + 1;   // ← ต้นเหตุ
order_number: generateOrderNumber(sequence)      // ORD-202609-0004
```

ตราบใดที่ไม่เคยลบออร์เดอร์ วิธีนี้ก็ใช้ได้ แต่พอ **รอบที่ 9 เพิ่มปุ่มลบคำสั่งซื้อ** เข้ามา
จำนวนออร์เดอร์ก็ลดลงได้ → `count()+1` ย้อนกลับไปชนเลขที่ที่ออกไปแล้ว → ชน `UNIQUE` ของคอลัมน์ `order_number`

ตัวอย่าง: มี 5 ใบ (0001–0005) ลบทิ้ง 2 ใบเหลือ 3 ใบ → ใบถัดไปได้เลข `0004` ซึ่งมีอยู่แล้ว → **P2002**

เป็นบั๊กที่ฟีเจอร์หนึ่ง (ลบออร์เดอร์) ไปทำให้อีกฟีเจอร์หนึ่ง (ออกเลขที่) พัง — ไม่ได้พังตั้งแต่แรก จึงเพิ่งโผล่ตอนใช้งานจริง

### วิธีแก้

**1. เดินเลขต่อจากเลขที่สูงสุดของเดือนนั้น ไม่ใช่จากจำนวนแถว**

```ts
const prefix = orderNumberPrefix();                     // "ORD-202609-"
const latest = await tx.order.findFirst({
  where: { order_number: { startsWith: prefix } },
  orderBy: { order_number: 'desc' },
});
const sequence = (latest ? orderNumberSequence(latest.order_number, prefix) : 0) + 1;
```

ลบออร์เดอร์เท่าไหร่เลขก็ไม่ย้อน เพราะอ่านจากเลขจริงที่ยังอยู่ในตาราง ไม่ใช่การนับ

**2. ลองใหม่อัตโนมัติเมื่อชนจริง ๆ** — แยก `createOnce()` ออกมา แล้วให้ `create()` เรียกซ้ำได้สูงสุด 3 ครั้งเมื่อเจอ `P2002`
กันกรณีสองคนกดสั่งพร้อมกันเป๊ะ ๆ (ทั้งคู่เห็นเลขสูงสุดเดียวกัน) และกันรหัส `pickup_code` ที่สุ่มมาแล้วดันซ้ำด้วย

### ไฟล์ที่แก้

| ไฟล์ | แก้อะไร |
|---|---|
| `src/common/utils/helpers.ts` | เพิ่ม `orderNumberPrefix()` · `orderNumberSequence()` · `generateOrderNumber()` รับ prefix ได้ |
| `src/orders/orders.service.ts` | `create()` เดินเลขจากเลขสูงสุด + ลองใหม่ได้ 3 ครั้ง (แยก `createOnce()`) |
| `API.md` | อธิบายวิธีออกเลขที่ใหม่ |

### ทดสอบยืนยัน

| กรณี | ผลลัพธ์ |
|---|---|
| ลบออร์เดอร์ 2 ใบ (0006, 0007) แล้วสั่งใหม่ 3 ครั้ง | ได้ 0006 → 0007 → 0008 ครบทั้งสามใบ ไม่มี error ✓ |
| ยิงคำสั่งซื้อพร้อมกัน 5 คำสั่ง (จำลอง race) | สำเร็จทั้ง 5 ใบ ได้ 0009–0013 **ไม่มีเลขซ้ำกันเลย** ✓ |
| ตรวจเลขที่ทั้งหมดในฐานข้อมูล | 13 ใบ ไม่ซ้ำกันสักใบ ✓ |

> หมายเหตุ: ถ้าลบออร์เดอร์ใบล่าสุดทิ้ง เลขของใบนั้นจะถูกนำกลับมาใช้ใหม่กับออร์เดอร์ถัดไป
> ยอมรับได้เพราะใบเดิมถูกลบไปแล้ว (ไม่มีสองใบที่ยังอยู่ถือเลขเดียวกัน)

## 2026-09-24 — รอบที่ 12: ระบบจัดส่งพัสดุ (เลขติดตาม + ปุ่มเช็คพัสดุ)

> ⚠️ **รอบนี้มีการเปลี่ยนโครงฐานข้อมูลอีกครั้ง** — ต้องรัน `npx prisma migrate deploy` แล้ว `npx prisma generate`

### สิ่งที่เพิ่ม

ออร์เดอร์แบบ "จัดส่งตามที่อยู่" เดิมจบแค่ตรงที่ลูกค้าเห็นข้อความว่า *"คำสั่งซื้อนี้เป็นแบบจัดส่ง"* แล้วก็ไม่รู้อะไรอีกเลย
รอบนี้ต่อให้ครบสองฝั่ง

**ฝั่งเจ้าหน้าที่ (`/staff/orders`)**

- ออร์เดอร์แบบจัดส่งมีปุ่ม **ใส่เลขพัสดุ** → กางฟอร์มใต้แถวนั้น เลือกบริษัทขนส่งจาก dropdown + กรอกเลขติดตาม
- คอลัมน์ "รับสินค้า" โชว์ชื่อขนส่งและเลขพัสดุที่บันทึกไว้ ถ้ายังไม่มีจะขึ้นเตือนสีส้มว่า "ยังไม่มีเลขพัสดุ"
- แท็บใหม่ **รอส่งพัสดุ** = จ่ายเงินแล้ว + เป็นแบบจัดส่ง + ยังไม่มีเลขพัสดุ (คือกองงานที่ต้องเอาของเข้าขนส่ง)
- ปุ่ม **ลูกค้าได้รับแล้ว** สำหรับปิดออร์เดอร์แบบจัดส่ง (แบบรับที่สาขาปิดผ่านหน้าจุดรับสินค้าเหมือนเดิม)
- ปุ่ม **ล้างข้อมูลจัดส่ง** เผื่อกรอกผิด

**ฝั่งลูกค้า (`/orders/[id]`)**

- การ์ดขวาเปลี่ยนจาก "บัตรรับสินค้า" เป็น **ข้อมูลการจัดส่ง** เมื่อออร์เดอร์เป็นแบบจัดส่ง
- แสดงชื่อบริษัทขนส่ง + เลขพัสดุตัวใหญ่ (คลิกเลือกทั้งก้อนได้) + **ปุ่มติดตามพัสดุ** ที่เปิดหน้าเช็คพัสดุของขนส่งนั้นพร้อมเลขในลิงก์
- ปุ่ม **คัดลอกเลขพัสดุ** เผื่อขนส่งที่รับเลขทาง URL ไม่ได้
- ยังไม่มีเลขพัสดุ → บอกตรง ๆ ว่ารอเจ้าหน้าที่ส่งของเข้าขนส่ง ไม่ปล่อยให้เดา
- **ไทม์ไลน์แยกสองแบบ** — แบบจัดส่งใช้ ชำระเงินแล้ว → กำลังเตรียมพัสดุ → ส่งเข้าขนส่งแล้ว → ได้รับพัสดุแล้ว
  (ของเดิมเขียนว่า "พร้อมรับสินค้า" ซึ่งไม่ตรงกับความจริงของออร์เดอร์ที่ส่งไปรษณีย์)

### ฝั่งฐานข้อมูล

migration `20260924090000_add_order_shipping_tracking` เพิ่ม 3 คอลัมน์ในตาราง `orders`

| คอลัมน์ | ชนิด | ใช้ทำอะไร |
|---|---|---|
| `shipping_carrier` | VARCHAR(50) | รหัสบริษัทขนส่ง เช่น `thailand_post`, `flash` |
| `tracking_number` | VARCHAR(50) (INDEX) | เลขติดตามพัสดุ |
| `shipped_at` | TIMESTAMPTZ | เวลาที่ส่งเข้าขนส่ง |

**เก็บเป็นรหัสขนส่ง ไม่ได้เก็บลิงก์ทั้งอัน** — ถ้าวันหนึ่งขนส่งเปลี่ยน URL หน้าเช็คพัสดุ
การเก็บลิงก์ไว้ในฐานข้อมูลแปลว่าต้องไล่แก้ข้อมูลเก่าทุกแถว เก็บแค่รหัสแล้วให้หน้าเว็บประกอบลิงก์เอง
รายชื่อขนส่งและแม่แบบลิงก์อยู่ที่ **`frontend/lib/carriers.js`** ที่เดียว (8 เจ้า: ไปรษณีย์ไทย, Flash, Kerry, J&T, Ninja Van, BEST, SCG, DHL)

### ฝั่ง API

`PATCH /api/orders/:id/shipping` รับ `{ shipping_carrier, tracking_number, mark_shipped? }`

1. ใช้ได้เฉพาะออร์เดอร์ `delivery_method: "delivery"` — ถ้าเป็น `pickup` ตอบ **422** ("ใช้รหัสรับสินค้าที่จุดรับแทน")
2. ใส่เลขพัสดุแต่ไม่เลือกขนส่ง → **422** (ลูกค้าจะไม่รู้ว่าต้องไปเช็คที่เว็บไหน)
3. ใส่เลขครั้งแรก → ตั้ง `shipped_at` และเลื่อน `order_status` เป็น `shipped` ให้อัตโนมัติ
   (ยกเว้นออร์เดอร์ที่ `completed` / `cancelled` อยู่แล้ว · ส่ง `mark_shipped: false` เพื่อข้าม)
4. ส่งค่าว่างทั้งสองช่อง = ล้างข้อมูลจัดส่งทิ้ง

`GET /api/orders?search=` ค้นจากเลขพัสดุได้ด้วยแล้ว (เพิ่มจากเลขที่ออร์เดอร์และรหัสรับสินค้า)

### ฝั่งฐานข้อมูล

### ฝั่ง API

| Method | Path | ทำอะไร |
|---|---|---|
| POST | `/api/uploads/image` | อัปโหลดรูป (multipart ฟิลด์ `file`) → คืน `url` |
| DELETE | `/api/uploads/image?url=...` | ลบไฟล์รูปที่ไม่ใช้แล้ว |
| GET | `/uploads/products/<ไฟล์>` | เปิดดูรูป (เสิร์ฟเป็น static ไม่มี prefix `/api`) |

- ใช้ `FileInterceptor` แบบเก็บไฟล์ในหน่วยความจำแล้วเขียนลงดิสก์เอง — **ไม่ต้องติดตั้ง `multer` หรือ `@types/multer` เพิ่ม**
  (ประกาศ interface ของไฟล์เองในไฟล์ controller) จำบทเรียนจากรอบ jsqr แล้วว่าการเพิ่ม dependency ทำให้ต้อง npm install ใหม่ทุกครั้ง
- รับเฉพาะ JPG PNG WEBP GIF · ไม่เกิน 5MB · **ตั้งชื่อไฟล์ใหม่แบบสุ่มเสมอ** ไม่ใช้ชื่อจากเครื่องผู้ใช้
  (กันทั้งไฟล์ชื่อซ้ำทับกัน และกันชื่อไฟล์แบบ `../../something` หลุดออกนอกโฟลเดอร์)
- `AllExceptionsFilter` แปลข้อความ `File too large` ของ multer เป็นภาษาไทย

### จุดที่ตั้งใจทำฝั่งหน้าเว็บ

- **รูปไม่มีก็ไม่พัง** — `ProductArt` รับ prop `src` เพิ่ม ถ้าไม่มีรูปหรือรูปโหลดไม่ขึ้น (`onError`) จะถอยไปวาดภาพ SVG ตามหมวดหมู่เหมือนเดิม

response แนบ `stock_restored: true/false` มาด้วย เพื่อให้ฝั่งหน้าเว็บ (และคนเทส) รู้ว่าระบบเลือกทางไหน

- **นับรวมออร์เดอร์ที่ยังรอยืนยันการชำระเงิน** เพราะสต็อกถูกตัดไปแล้วตั้งแต่ตอนสั่ง — เขียนกำกับไว้ใต้หัวข้อ
- เรียงตามสินค้าที่ขายดีที่สุดก่อน · ชื่อสินค้าโชว์เฉพาะแถวแรกของกลุ่ม อ่านเป็นก้อนได้
- สินค้าพรีออเดอร์ขึ้น "ไม่จำกัด" ในช่องคงเหลือ เพราะสั่งได้แม้สต็อกเป็น 0

- ปุ่มส่งออก CSV แยกของตัวเอง (รวม BOM ให้ Excel อ่านภาษาไทยออก)

## 2026-09-23 — รอบที่ 7: แก้บั๊ก ออร์เดอร์ไม่ขึ้นในระบบเจ้าหน้าที่

### อาการ

สั่งซื้อจากหน้าร้านสำเร็จ แต่หน้าเจ้าหน้าที่มองไม่เห็นออร์เดอร์นั้น

### สาเหตุ

**ข้อมูลเข้าฐานข้อมูลครบถ้วน** — ตรวจด้วย API แล้วเจอออร์เดอร์จริง

```
ORD-202609-0003 | payment: pending        | slip: ไม่มี   ← หายไปจากหน้าเจ้าหน้าที่
ORD-202609-0002 | payment: waiting_verify | slip: มี
ORD-202609-0001 | payment: paid           | slip: มี
```

ปัญหาอยู่ที่ **หน้าเจ้าหน้าที่กรองทิ้ง** — ตาราง "สลิปที่รอตรวจสอบ" กรองเฉพาะ `payment_status === 'waiting_verify'`
ซึ่งเป็นสถานะของออร์เดอร์ที่ **แนบสลิปมาแล้ว** เท่านั้น

แต่การแนบสลิปเป็น "ไม่บังคับ" ที่หน้าเช็คเอาต์ ถ้าลูกค้าไม่แนบ backend จะตั้ง `payment_status = 'pending'`
(ดู `orders.service.ts`: `payment_status: dto.payment_slip ? 'waiting_verify' : 'pending'`)
ออร์เดอร์แบบนี้จึงไม่เข้าเงื่อนไขของตาราง และไม่มีหน้าไหนในระบบเจ้าหน้าที่แสดงมันเลย
เป็นช่องโหว่ในการออกแบบหน้าจอ ไม่ใช่บั๊กของ backend หรือฐานข้อมูล

### วิธีแก้

1. **เพิ่มหน้า `/staff/orders`** — คำสั่งซื้อทั้งหมด มีแท็บ "ต้องดำเนินการ / ชำระแล้ว / ทั้งหมด"
   พร้อมป้ายนับจำนวนงานค้าง ปุ่ม **ยืนยันรับเงิน** · **ปฏิเสธ** · **แจ้งว่าของพร้อม**
   ตอนนี้ไม่มีออร์เดอร์ไหนหายไปจากสายตาเจ้าหน้าที่แล้ว
2. **`/staff/stock`** — เปลี่ยนเงื่อนไขเป็น `pending` **หรือ** `waiting_verify`
   เปลี่ยนหัวข้อเป็น "คำสั่งซื้อที่รอตรวจการชำระเงิน" และเพิ่มคอลัมน์ "สถานะสลิป"
   ที่แยกชัดว่า *แนบสลิปแล้ว* หรือ *ยังไม่แนบสลิป* · เรียงอันที่มีสลิปขึ้นก่อนเพราะตรวจได้เลย
3. **`/staff` ภาพรวม** — การ์ด "สลิปรอตรวจ" เปลี่ยนเป็น "รอยืนยันการชำระเงิน" และนับทั้งสองสถานะ
4. **เมนูข้าง** — เพิ่ม "คำสั่งซื้อ" และตัดเมนู "ตรวจสลิป"/"รายงาน" ที่ยังไม่มีหน้าจริงออก

### ทดสอบยืนยัน

จำลองสิ่งที่ผู้ใช้ทำเป๊ะ ๆ (สั่งซื้อโดยไม่แนบสลิป) แล้วเดินต่อจนจบ

```
สั่งซื้อไม่แนบสลิป → ORD-202609-0003                      ✅
เห็นใน /staff/orders · ขึ้นว่า "ยังไม่แนบ"                  ✅
เห็นใน /staff/stock (เดิมมองไม่เห็น)                       ✅
กดยืนยันรับเงิน → paid + confirmed                        ✅
จุดรับสินค้าขึ้น "พร้อมส่งมอบ"                              ✅
ไม่มี console error                                       ✅
```

## 2026-09-23 — รอบที่ 6: เปลี่ยน frontend เป็น Next.js

### เหตุผล

รอบที่ 5 ทำเป็น React + Vite ไว้ แต่ต้องการ **Next.js** จึงย้ายทั้งหมด
หน้าตา ฟีเจอร์ และ API ที่ใช้เหมือนเดิมทุกอย่าง — เปลี่ยนแค่โครงและวิธี routing

### สิ่งที่เปลี่ยน

| เรื่อง | Vite (เดิม) | Next.js (ใหม่) |
|---|---|---|
| Routing | `react-router-dom` ประกาศเส้นทางใน `App.jsx` | App Router — โฟลเดอร์ใน `app/` คือเส้นทาง |
| Layout ร่วม | `<Route element={<ShopLayout/>}>` | `app/(shop)/layout.jsx` และ `app/staff/layout.jsx` |
| Proxy API | `server.proxy` ใน `vite.config.js` | `rewrites()` ใน `next.config.mjs` |
| ลิงก์ | `<Link to=...>` | `<Link href=...>` จาก `next/link` |
| เมนูที่ไฮไลต์ | `<NavLink>` | `usePathname()` จาก `next/navigation` |
| เปลี่ยนหน้าหลังสั่งซื้อ | `useNavigate()` | `useRouter().push()` |
| อ่าน `:id` | `useParams` ของ react-router | `useParams` ของ `next/navigation` |
| ฟอนต์ | `<link>` ไป Google Fonts | `next/font/google` (โหลดแบบ self-host) |
| พอร์ต | 5173 | **4000** |

### เรื่องที่ต้องระวังตอนย้าย

- **`'use client'`** — หน้าที่มี state/ปุ่ม/ฟอร์ม ต้องใส่บรรทัดนี้บนสุด ส่วน layout ทั้งสองอันไม่มี state
  จึงปล่อยเป็น server component ได้ ไม่ต้องส่ง JS ของมันไปเบราว์เซอร์
- **hydration mismatch จากตะกร้า** — เดิมอ่าน `localStorage` ตอน `useState` เริ่มต้น พอมาเป็น Next
  ฝั่ง server ไม่มี `localStorage` ทำให้ HTML สองฝั่งไม่ตรงกัน แก้โดยเริ่มด้วยค่าว่างเสมอ
  แล้วอ่าน `localStorage` ใน `useEffect` พร้อมธง `ready` ให้หน้าเช็คเอาต์รอก่อนตัดสินว่าตะกร้าว่าง
- **ช่องค้นหา** — เดิมส่งค่าด้วย `window.dispatchEvent` ซึ่งไม่เข้ากับวิธีคิดของ Next
  เปลี่ยนเป็น `SearchProvider` เล็ก ๆ ใน `app/(shop)/layout.jsx`
- **route group `(shop)`** — วงเล็บทำให้ใช้ layout ร่วมกันได้โดยชื่อโฟลเดอร์ไม่โผล่ใน URL

### ทดสอบแล้ว

`npm run build` ผ่าน ไม่มี error แล้วรัน `npm start` คู่กับ backend เดินครบทุกหน้าด้วยเบราว์เซอร์จริง (Playwright)

```

หน้าแรก             โหลดสินค้าจาก DB · กรอง · หยิบลงตะกร้า        ✅
เช็คเอาต์            แนบสลิป → สั่งซื้อ → ORD-202609-0003          ✅
บัตรรับสินค้า         ไทม์ไลน์ + QR canvas จาก pickup_code จริง    ✅
สต็อก/สลิป           อนุมัติสลิปของออร์เดอร์นั้น → paid + confirmed  ✅
จุดรับสินค้า          ตรวจรหัส → ส่งมอบ → completed                ✅
กลับดูบัตร           ขึ้น "รับสินค้าเรียบร้อยแล้ว"                   ✅
```

## 2026-09-22 — รอบที่ 4: เขียน backend ใหม่เป็น NestJS

### เหตุผล

รอบก่อนหน้าเขียน API เป็น Express ไว้ แต่ backend ของโปรเจกต์จริงคือ **NestJS** จึงรื้อเขียนใหม่ทั้งหมด
ฐานข้อมูลไม่กระทบ — `schema.prisma`, migration และข้อมูลใน `csmju_shop` ใช้ของเดิมต่อได้เลย

### สิ่งที่เปลี่ยน

- **ลบ `src/` ของ Express ทิ้งทั้งหมด** เขียนใหม่เป็น NestJS 12 (TypeScript)
- **โครงสร้างแบบ module** — แต่ละ feature มี `*.module.ts` / `*.controller.ts` / `*.service.ts` / `dto/`
  แยกหน้าที่ชัดเจน: controller รับ-ส่ง HTTP, service ถือ business logic, DTO ถือกฎการตรวจข้อมูล
- **`PrismaService`** สืบทอดจาก `PrismaClient` ใช้ `OnModuleInit` / `OnModuleDestroy`
  จัดการ connection ตาม lifecycle ของ Nest และลงทะเบียนเป็น `@Global()` module
- **DTO + class-validator** ตามที่ตกลงไว้ — ย้ายการตรวจข้อมูลออกจาก service มาไว้ที่ DTO
  `ValidationPipe` ตั้ง `whitelist: true` (ตัดฟิลด์แปลกปลอม) และ `errorHttpStatusCode: 422`
- **`TransformInterceptor`** ห่อ response ทุกอันเป็น `{ success, message, data, meta? }` ที่เดียว
  ไม่ต้องเขียนซ้ำในทุก controller เหมือนตอนเป็น Express
- **`AllExceptionsFilter`** แปลง exception ทุกชนิด รวม Prisma error code เป็น HTTP status
- **`setGlobalPrefix('api')`** ยกเว้นหน้าแรก `/`

### ปัญหาที่เจอระหว่างทาง

| ปัญหา | สาเหตุ | วิธีแก้ |
|---|---|---|
| `nest build` ฟ้องว่า TypeScript 7.0.2 ไม่มี compiler API | TS 7.0 ปล่อยมาเฉพาะตัว `tsc` ยังไม่มี programmatic API (จะกลับมาใน 7.1) | ใช้ `typescript@^6.0.3` แทน |
| TS6 ฟ้อง `TS2564: Property has no initializer` ในทุก DTO | TS6 เข้มขึ้นเรื่อง strictPropertyInitialization | ตั้ง `"strictPropertyInitialization": false` ตามที่ template ของ NestJS 12 ใช้ |
| `TS1479: referenced file is an ECMAScript module` ทุกไฟล์ที่ import `@nestjs/common` | **NestJS 12 เป็น ESM อย่างเดียว** (`"type": "module"` ใน package ของมัน) | เปลี่ยนโปรเจกต์เป็น ESM ทั้งหมด (ดูด้านล่าง) |

### การย้ายไปเป็น ESM

1. เพิ่ม `"type": "module"` ใน `package.json`
2. `tsconfig.json` ใช้ `module`/`moduleResolution` เป็น `nodenext` ตาม template ของ NestJS 12
3. **เติม `.js` ต่อท้าย import ที่อ้างไฟล์ในโปรเจกต์ทุกจุด** (34 ไฟล์)
   เช่น `import { UsersService } from './users.service.js';`
   — ไม่ใช่พิมพ์ผิด ESM อ้างถึงไฟล์ผลลัพธ์หลังคอมไพล์ซึ่งเป็น `.js`
4. เปลี่ยนชื่อ `prisma/seed.js` → **`prisma/seed.cjs`** เพราะยังใช้ `require()` อยู่
   (ในโปรเจกต์ ESM ไฟล์ `.js` จะถูกอ่านเป็น ES module ทันที)

## 2026-09-22 — รอบที่ 3: แก้ error P3005 (ฐานข้อมูลมีตารางอยู่แล้วแต่ไม่มีประวัติ migration)

### ปัญหา

```
Error: P3005
The database schema is not empty.
```

**สาเหตุ:** ฐานข้อมูล `csmju_shop` ถูกสร้างตารางไว้แล้วจาก `prisma db push` ที่เคยรันก่อนหน้านี้
`db push` สร้างตารางให้ก็จริง แต่ **ไม่บันทึกประวัติลงตาราง `_prisma_migrations`**
พอมารัน `migrate deploy` Prisma เห็นว่ามีตารางอยู่แล้วแต่ไม่รู้ว่ามาจาก migration ไหน จึงไม่กล้าแตะต้องและหยุดทันที

### วิธีแก้

```powershell
npx prisma migrate reset --force
npm run seed
```

**ทำไมไม่ใช้วิธี baseline** (`prisma migrate resolve --applied ...`)
เพราะตารางเดิมที่ `db push` สร้างไว้ มาจาก schema รุ่นก่อนซึ่งต่างจากรุ่นปัจจุบันหลายจุด —
`role`/`payment_status`/`order_status` เปลี่ยนจาก `VARCHAR(50)` เป็น `VARCHAR(20)`, เพิ่ม index 9 ตัว,
เพิ่ม `UNIQUE (product_id, variant_name)`, เปลี่ยน `TIMESTAMP` เป็น `TIMESTAMPTZ`
ถ้า baseline ไปเฉย ๆ Prisma จะคิดว่า migration ถูก apply แล้วทั้งที่โครงสร้างจริงยังเป็นของเก่า
ฐานข้อมูลกับ schema จะไม่ตรงกันและไปพังทีหลัง — `reset` จึงตรงไปตรงมากว่า
ข้อมูลที่หายมีแค่ข้อมูล seed ซึ่ง `npm run seed` สร้างกลับมาได้ทันที

### ทดสอบยืนยัน

จำลองสภาพเดียวกัน (สร้าง DB → `db push` → `migrate deploy`) ได้ P3005 เหมือนกันเป๊ะ แล้วรันวิธีแก้

```
1) npx prisma migrate reset --force  → Database schema is up to date! ✅
2) npm run seed                      → users 4 / products 4 / variants 9 / orders 2 ✅
3) newman                            → 52 requests / 129 assertions ผ่านทั้งหมด ✅
```

## 2026-09-22 — รอบที่ 2: แก้ขั้นตอนติดตั้งให้ไม่ต้องใช้ psql


**สาเหตุ:** PostgreSQL installer บน Windows ไม่ได้เพิ่มโฟลเดอร์ `bin` เข้า PATH ตัว `psql.exe`

### วิธีแก้

ตัดขั้นตอน `psql -U postgres -c "CREATE DATABASE csmju_shop;"` ออกจากคู่มือทั้งหมด
เพราะ **`npx prisma migrate deploy` สร้างฐานข้อมูลให้เองอยู่แล้วถ้ายังไม่มี** — ไม่จำเป็นต้องใช้ psql เลย

ทดสอบยืนยันแล้ว: ลบฐานข้อมูลทิ้งทั้งก้อน แล้วรันจากศูนย์

```

2) npx prisma generate        → Generated Prisma Client ✅
3) npm run seed               → users 4 / products 4 / variants 9 / orders 2 ✅
4) newman                     → 52 requests / 129 assertions ผ่านทั้งหมด ✅
```
